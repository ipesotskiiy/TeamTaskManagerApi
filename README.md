# Team Task Manager API

REST API для совместного управления рабочими пространствами, задачами и участниками команды, реализованный на FastAPI и SQLAlchemy.

Приложение позволяет пользователям создавать рабочие пространства, управлять составом команды и ролями участников, создавать и назначать задачи, оставлять комментарии и отслеживать историю изменений.

Основное внимание в проекте уделено:

- разграничению прав доступа;
- изоляции данных между рабочими пространствами;
- транзакционной целостности;
- валидации входных данных;
- обработке конфликтов;
- миграциям базы данных;
- автоматизированному тестированию;
- разделению API, бизнес-логики и работы с данными.

---

## Основные возможности

### Аутентификация

Реализованы:

- регистрация пользователей;
- JWT-аутентификация;
- безопасное хеширование паролей;
- получение данных текущего пользователя;
- валидация email;
- валидация минимальной длины username;
- валидация минимальной длины password;
- защита от регистрации пользователя с уже существующим email;
- защита от регистрации пользователя с уже существующим username;
- обработка конфликтов уникальности на уровне базы данных.

Требования к регистрации:

- email должен иметь корректный формат;
- username должен содержать не менее 5 символов;
- password должен содержать не менее 10 символов.

JWT `SECRET_KEY` не хранится непосредственно в исходном коде и загружается через настройки окружения.

## Рабочие пространства

Пользователь может:

- создать рабочее пространство;
- получить список доступных ему рабочих пространств;
- получить конкретное рабочее пространство;
- изменить рабочее пространство;
- удалить рабочее пространство.

При создании рабочего пространства пользователь автоматически становится его владельцем и получает роль:

```text
owner
```

---

## Участники рабочего пространства

Поддерживаются три роли:

- `owner` — владелец;
- `admin` — администратор;
- `member` — обычный участник.

Реализованы:

- получение списка участников;
- получение конкретного участника;
- фильтрация участников по роли;
- пагинация;
- добавление участника;
- изменение роли участника;
- удаление участника.

### Права на управление участниками

`owner` может:

- добавлять `member`;
- добавлять `admin`;
- изменять роли участников;
- удалять `member`;
- удалять `admin`.

`admin` может:

- добавлять `member`;
- удалять `member`.

`member` не может управлять составом рабочего пространства.

Для владельца рабочего пространства действуют дополнительные ограничения:

- нельзя изменить роль существующего `owner`;
- нельзя назначить другого пользователя `owner`;
- нельзя удалить `owner`.

При удалении участника все задачи текущего рабочего пространства, назначенные на этого пользователя, автоматически становятся неназначенными.

Задачи других рабочих пространств при этом не изменяются.

## Задачи

Реализованы:

- создание задачи;
- получение списка задач;
- получение конкретной задачи;
- изменение задачи;
- удаление задачи;
- пагинация;
- фильтрация по статусу;
- фильтрация по приоритету;
- фильтрация по исполнителю.

Поддерживаемые статусы:

- `todo`;
- `in_progress`;
- `done`.

Поддерживаемые приоритеты:

- `low`;
- `medium`;
- `high`.

У задачи могут отсутствовать:

- исполнитель;
- срок выполнения.

Исполнителем задачи может быть только пользователь, состоящий в соответствующем рабочем пространстве.

---

## Права на изменение задач

`owner` и `admin` имеют расширенные права на изменение задач.

Создатель задачи может изменять:

- название;
- описание;
- приоритет;
- срок выполнения.

Исполнитель задачи может изменять:

- статус.

Если пользователь одновременно является создателем и исполнителем задачи, его права объединяются.

Удалять задачу могут:

- `owner`;
- `admin`;
- создатель задачи.

## Изоляция данных

Основные ресурсы API ограничиваются рабочим пространством.

Пользователь не получает доступ к данным рабочего пространства, участником которого он не является.

При поиске:

- задач;
- комментариев;
- участников;
- записей активности

учитывается принадлежность ресурса к соответствующему рабочему пространству.

Это предотвращает доступ к ресурсам другого workspace простой подстановкой чужого идентификатора в URL.

---

## HTTP-коды

В API используются следующие основные HTTP-коды:

- `200 OK` — успешное получение или изменение данных;
- `201 Created` — успешное создание ресурса;
- `204 No Content` — успешное удаление ресурса;
- `400 Bad Request` — нарушение бизнес-правил запроса;
- `401 Unauthorized` — отсутствующая или некорректная аутентификация;
- `403 Forbidden` — пользователь аутентифицирован, но не имеет необходимых прав;
- `404 Not Found` — ресурс отсутствует или недоступен в текущей области видимости;
- `409 Conflict` — конфликт с уже существующими данными;
- `422 Unprocessable Content` — ошибка валидации входных данных.

---

## Транзакционная целостность

Операции, представляющие одно бизнес-действие, выполняются как единая транзакция.

Например, при удалении участника рабочего пространства:

1. у назначенных на него задач снимается исполнитель;
2. удаляется запись `WorkspaceMember`;
3. изменения фиксируются одним `commit`.

Это предотвращает частичное сохранение бизнес-операции.

---

## Защита уникальности

Для формирования понятных ответов API перед созданием некоторых сущностей выполняются предварительные проверки существования данных.

При этом окончательная гарантия целостности обеспечивается ограничениями базы данных.

Возможные конфликты при конкурентных запросах обрабатываются через:

```text
IntegrityError
        ↓
rollback
        ↓
409 Conflict
```

Такой подход применяется при:

- регистрации пользователя;
- добавлении пользователя в рабочее пространство.

---

## Массовое обновление задач

При удалении участника рабочего пространства связанные задачи не загружаются целиком в Python для изменения в цикле.

Для снятия исполнителя используется один SQL `UPDATE`, ограниченный:

- идентификатором рабочего пространства;
- идентификатором удаляемого пользователя.

После этого удаляется `WorkspaceMember`, а вся операция фиксируется одним `commit`.

## Особенности реализации

### Синхронный SQLAlchemy

В проекте используется синхронная SQLAlchemy `Session`.

Поэтому endpoint'ы, выполняющие синхронную работу с базой данных, реализованы через обычные:

```python
def
```

Это позволяет не выполнять блокирующие вызовы синхронного SQLAlchemy непосредственно внутри `async def`.

---

### Dependency layer

Повторно используемая логика вынесена из router-функций в отдельный слой:

```text
app/api/v1/dependencies/
```

В нём находятся:

- поиск ресурсов;
- проверки существования;
- проверки ролей;
- проверки прав;
- валидация исполнителей;
- подготовка данных для обновления;
- общие запросы к membership.

---

### Service layer

Логика формирования записей журнала активности вынесена в:

```text
app/services/task_activity.py
```

Это позволяет отделить создание `TaskActivity` от HTTP-обработчиков.

---

### Конфигурация базы данных

`DATABASE_URL` имеет единый источник:

```text
settings.DATABASE_URL
```

Он используется как приложением, так и Alembic.

Это предотвращает ситуацию, когда приложение и миграции работают с разными базами данных из-за независимых настроек.

---

### Секрет JWT

`SECRET_KEY` является обязательной настройкой.

Он загружается через Pydantic Settings из окружения и не имеет hardcoded значения по умолчанию.

---

### Контроль целостности данных

Бизнес-проверки в API дополняются ограничениями базы данных.

Для операций, способных столкнуться с конфликтом уникальности, предусмотрены:

- предварительная проверка;
- DB constraint;
- обработка `IntegrityError`;
- `rollback`;
- ответ `409 Conflict`.

---

### Изоляция ресурсов

Поиск вложенных ресурсов выполняется с учётом их родительского контекста.

Например:

```text
workspace
   ↓
task
   ↓
comment / activity
```

Это позволяет ограничивать доступ к ресурсу не только его идентификатором, но и принадлежностью к соответствующему workspace/task.
